# 设计笔记

这份文档记录"为什么这样做"，而不是"做了什么"。做了什么看 README。

---

## 1. 为什么是 GitHub Action，而不是对话式 Skill

本届比赛里绝大多数作品是"在对话框里问我点什么"。这是合理的——麦当劳 MCP 的数据天然适合对话。
但我们刻意选了另一条路，原因有三个：

**（1）触发点不在人的注意力里。**
点餐是"我想吃的时候"才发生的行为，需要用户主动唤起。而 PR 合并是**已经在发生的团队行为**，
每天多次，发生在开发者注意力最集中的地方（代码评审界面）。把税单挂在这个动作上，
不需要用户记得"还有个 Skill 可以玩"。

**（2）产物天然可传播。**
一张 ASCII 小票是**截图友好的**。它出现在 Slack、周报、群里，而对话框里的回答不会。
更关键的是：税单印在别人仓库的 PR 里，每个看到的人都可能想"我们组也装一个"——
这是这个项目唯一可能规模化的增长机制，所以票据底部必须有 2 分钟的安装路径。

**（3）技术约束逼出了好设计。**
GitHub Actions 环境很窄：不能保证有 npm install、不能读用户源码、要能在 60 秒内跑完。
这些限制直接决定了项目的三个硬指标：零依赖、只用 REST API 的统计数字、三级降级。

## 2. 计税：为什么是"加性 + 乘性 + 夹紧"

### 为什么不用单一公式

最初的设计是 `Score = 新增×1.0 + 删除×1.5 + 提交×30` 这类加权求和（这也是大多数同类项目的做法）。
它的问题不是不准确，而是**不可解释**：

- 用户看到"3.7 只"会问"为什么是 3.7"，而你只能回答"公式是这样的"；
- 想调整某一项权重，会同时改变所有场景的结果，无法做局部校准。

所以《麦门税法》改成两层结构：

```
加性小计 = T1 + T2 + T3          // 每一项都能独立解释、独立封顶
应纳     = round(加性小计 × Π乘数)  // 乘数只表达"这件事让税变重/变轻多少"
最终     = clamp(应纳, 1, 12)      // 破产保护，防止极端 PR 把同事吃破产
```

好处是**每一层都可以单独讨论**：
"500 行才加一只太宽松了" → 只改 `codeLinesPerUnit`；
"周末 1.5 倍不够狠" → 只改 `M2` 的乘数；
这两件事互不影响，测试也能分别锁。

### 为什么附加税是配菜而不是倍数

周五夜间 ×2 之外还"加征 1 份薯条"，周末 ×1.5 之外还"加征 1 杯美式"。
这是刻意的**双重表达**：

- 倍数改动的是"巨无霸的数量"，是可计算的、连续的量；
- 配菜改动的是"购物篮的构成"，是不可分割的、离散的量。

如果把薯条折算成 0.3 只巨无霸，会有两个后果：税单金额变得不像真的（谁见过 3.3 个汉堡），
而且用户没法真的照着买。用配菜表达，购物篮就能直接照单点餐。

### 为什么是四舍五入而不是向上取整

上一版用的是 `Math.ceil`（"凑不齐也要买一只"）。它更好玩，但会让 1.1 只变成 2 只，
在 2 只以内的区间里产生 80% 的偏差，用户会觉得税太重且不讲理。
`round` 的偏差最多半只，而且 `4.5 → 5` 这种例子说明它并不"宽松"。
更重要的是：**规则必须能一句话说清**。"四舍五入"谁都懂，"向上取整"需要解释。

### 为什么下限是 1、上限是 12

下限 1 是为了让"只改了个 typo"的人也被盖个章——税单是个社交道具，0 只就没有道具了。
上限 12 是因为**这是请客，不是罚款**：12 只巨无霸 ≈ ¥306，已经是"这个季度的锅你背了"的量级。
上限可通过 `max-burgers` 输入调，但默认值必须保守。

## 3. 核价：为什么需要一张二维回退表

核价不是"调一次接口"，而是"在不可控的现实里找到一条能出价的路"。实测踩到的四个约束：

1. **早餐时段（05:14–10:15）门店菜单里没有巨无霸**。不是报错，是菜单里就没有这个 key。
2. **打烊门店的 `query-meals` 返回空菜单**（0 条），而不是报错。所以"这家店能不能用"
   只能靠"试着取一次菜单"来判定，看 `businessStatus` 不够。
3. **算价接口会拒绝不可售商品**（`code=60006`），即使菜单里还挂着它的价格。
4. **深夜全城打烊**，任何一家店都出不了菜单。

于是有了这条链：

```
① 当前时段 × 逐家门店      → 有一家能出菜单且有巨无霸 → 算价成功就收工
② 预约最近午餐时段 × 逐家   → 解决早餐期
③ 深夜兜底（24h 门店）      → 解决全城打烊，标记 afterHours
④ 菜单标价求和             → 算价挂了但菜单有价，比快照真实
⑤ 离线快照                 → 彻底没网/没 Token
```

**为什么门店要排在时段前面**：因为"现在就能吃到"比"预约中午"更符合税单的用途（下班顺路清税）。
先扫完所有店的"当前时段"，再统一进"预约时段"。

**为什么指定了 `store-code` 就不换店**：小票上写着门店名，用户会真的去那家店。
如果为了核出价格偷偷换成另一家，就是把技术便利转嫁成用户的麻烦。
唯一的例外是 24h 兜底，且必须在票面写明"周边已打烊，按 24 小时门店核价"。

## 4. MCP 协议：三个必须写死的细节

### 4.1 `notifications/initialized` 的 202

按规范，初始化后要发一条通知，服务端返回 **202 + 空 body**。
把"空 body"当成异常是很容易犯的错——因为大多数 HTTP 客户端会把"没有 JSON"视作失败。
后果是每条链路都白重试一次（在 Actions 里表现为莫名其妙的 2× 耗时）。

```js
if (res.status === 202 || res.status === 204) return { empty: true }; // 这不是错误
```

### 4.2 `structuredContent` 优先于文本

服务端同时给了两份数据：`content[0].text`（人读的 Markdown + 内嵌 JSON）和
`result.structuredContent`（结构化对象）。实测一次 `query-meals` 的 text 有 **28 KB**，
其中绝大部分是字段说明文字。

踩过的坑：`available-coupons` 的返回形态**不稳定**——有时是结构化券数组
（`couponName` / `couponStatus:"CAN_GET"`），有时只有 Markdown 列表。
如果只写一种解析，就会静默漏数据（不报错，只是小票上少一行）。
所以顺序必须是：结构化 → 文本 → 都没有就空着，且**绝不编造**。

### 4.3 单位：元与分不能混用

- `query-meals` 的 `currentPrice` 是**元**（字符串 `"25.5"`）；
- `calculate-price` 的 `price` / `discount` / `productList[].subtotal` 是**分**（整数 `7650`）。

混用会差 100 倍，而且因为都是"看起来合理的数字"，测试很难发现。
项目里的做法是：**所有内部计算一律用分**，只在渲染时除以 100。

另一个只有算价接口才给得出的信息：
美式菜单标价 11.9 元，但 `calculate-price` 按原价 19 元起算、给 7.1 元优惠。
自己按"菜单价 × 数量"求和，总额碰巧相等，但"优惠"一栏会写成 0——**数字对、口径错**。
这就是坚持走 `calculate-price` 而不是自己乘的理由。

## 5. 小票排版：中文为什么不能按字符数对齐

等宽字体里，一个汉字占 2 列，一个英文/数字占 1 列。用 `String.length` 算宽度，
`T1 基础合并税` 会被算成 8 个字符，实际占 15 列——整张小票会从中段开始歪。

所以有了 `displayWidth()`：按码点判断东亚宽度区间，汉字算 2，其余算 1。
在此之上还做了两件中文排版必须做的事：

**避头点**：`，。、；：` 这类标点不能落在行首。实现方式是"悬挂"——
宁可让这一行超宽 2 列，也要把标点粘在上一行末尾。所以测试里允许 `行宽 ≤ 48 + 2`。

**词内不断行**：`2026-10-21`、`11:30` 不能被拦腰截断。
实现上先把文本切成"不可再分的排版单元"（CJK 一字一元，ASCII 连续串整体一元），再做贪心填充。

还有一个细节：地址长度不定。放得下就按两列对齐（`地址 …… 336号`），
放不下才折行——否则会出现"商户右对齐、地址左对齐"的突兀感。

## 6. 时间：Actions 跑在 UTC 上

GitHub Actions 的默认时区是 UTC。判断"周五夜间""周末"时，如果直接用
`new Date().getDay()`，在北京时间周五 20:00 会得到"周五 12:00"——附加税直接消失。

所以计税内核不碰 `Date` 的本地方法，而是**手工加偏移**：

```js
const d = new Date(t.getTime() + offsetHours * 3600 * 1000);
d.getUTCDay();  // 这才是"东八区的星期几"
```

偏移可配置（`utc-offset` 输入），因为"深夜"的定义本来就该由用户决定。

同一个坑在演示脚本里也踩过一次：把"东八区墙上时间"当成 UTC 去 `toISOString()`，
结果周五 19:04 变成了周六 03:04，附加税从"周五夜间"错判成"周末"。
修法是显式减 8 小时。这类 bug 的特点是**看起来完全正常**，只有检查票面星期几才会发现。

## 7. 测试策略：把契约钉死，而不是追求覆盖率

78 个用例，分布很偏：

| 文件 | 数量 | 为什么这么多 |
| --- | --- | --- |
| `tax.test.js` | 26 | 税法规则是产品核心，每条都要有正例 + 边界反例 |
| `mcp.test.js` | 16 | 协议细节不可靠外部网络测，用 mock fetch 钉死 |
| `assess.test.js` | 13 | 回退链路的每个分支都对应一种真实故障 |
| `receipt.test.js` | 11 | 排版是"看起来对不对"，只能靠断言宽度与关键字 |
| `comment.test.js` | 12 | 评论是交付物本体，marker/围栏/文案都要锁 |

三条原则：

**（1）只测纯函数和可注入依赖。**
`computeTax` 不碰 IO；`assess` 只依赖一个鸭子类型的 client（`callToolData` / `callTool`）；
传输层用 `globalThis.fetch` 打桩。这样测试不需要网络、不需要 Token、跑完 0.3 秒。

**（2）测"不能发生的事"。**
比"能算对"更重要的是"不会算错"：
加分不能变负、`×0.5`×`×2` 不能漏乘、快照模式不能声称实时、券解析不出来不能编造、
下架商品不能塞进算价请求、marker 必须在首行（否则重复开票）。

**（3）测试名字写成人话。**
`'⑤ 深夜周边全打烊（全空菜单）→ 24h 门店兜底并标记 afterHours'`
——失败时不需要去看代码就知道哪条产品规则破了。

## 8. 已知局限

诚实列出来，比藏起来好：

1. **快照价格是静态的**。`data/menu-snapshot.json` 记的是 2026-10-21 的上海价格。
   跨城市或调价后会有偏差，票面会标注「离线快照模式」。
2. **门店选择是"最近的一家"**，不判断你是否真的会去。`mcd-keyword` 只能给个大致区域。
3. **没有历史记录**。零存储是设计取舍——但也意味着无法回答"我这个月交了多少税"。
   要做的话，得引入外部存储，会破坏"零配置接入"。
4. **深夜兜底会改变取餐门店**。票面写明了，但对第一次看到的人来说仍可能困惑。
5. **团队规模大时税单会刷屏**。每个 PR 一条评论，50 人的团队一天可能十几条。
   缓解手段是 `comment: false` 只打日志，但那也就失去了传播性。

## 9. 与同类项目的差异

这届比赛里"代码 → 巨无霸"已经有作品（例如 `git-to-big-mac-hedger`：读本地 git log，
算努力分 → 热量上限 → 推荐套餐，输出终端账单）。差别在三点：

| | 同类 CLI | 本项目 |
| --- | --- | --- |
| 触发 | 用户手动跑命令 | CI 里自动触发 |
| 对象 | 我今天该犒赏多少 | 我该请同事多少 |
| 价格 | 菜单价 + 折扣率 | `calculate-price` 实付价（含优惠，单位分） |
| 产物 | 终端文本 | 可截图的 ASCII 凭证，印在 PR 里 |

不是"更好"，是**不同的问题**：一个是自我犒赏，一个是团队契约。
